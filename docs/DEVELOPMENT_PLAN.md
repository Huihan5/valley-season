### 3.4 文本"这句话什么时候成立"的审查：第一轮已修

检查的问题：这句话在什么时候成立？日期、时段、天气、地点、人物在场、关系、首次／重复、前置行动、已知信息、实际资源结算。固定事件、随机事件、普通闲笔都要查，不能只审润色。规则性原则在 GDD_NEXT 11.5。

**工具**：`npm run audit`（`scripts/audit-text.ts`；`-- --rule time` 只看一类，`-- --out design-drafts/audit-report.md` 存成文件（`design-drafts/` 不进 git））。它先算出每段文字能在哪些时段、天气、日期出现（场景和事件看数据本身的结构，行动结果和招呼看模拟赛季里真正出现的情形，有出现条件的句子按条件收窄），再列出说了"雨／傍晚／上个月／周三"却没有条件保证的句子。只提问题，不下结论；多数命中是"没问题"（句子在讲过去、讲将来、比较，或者结果文字本来就跨过一个时段）。文字改过之后可以重跑。

**第一轮（2026-10-08）已修**，见 CHANGELOG `续六`：日历（Day 6 的"六天"、邮差"每周二"、Day 23"还有七天"、第二幕底文"十月走到了中段"）、休整三段改成晚上的事、Day 15 "午饭前"、"上个月"改"月初"、五段"阳光"的地点底文改成不依赖天气、"你上周随口说过喜欢的"去掉"上周"、氛围里"这一天已经没有别的事要做了"删去。氛围、行动结果、天气句里只在某种条件下成立的句子加了出现条件（`config.ts` 的 `AMBIENT_RULES` / `RESULT_RULES` / `WEATHER_LINE_RULES`，按句子在池里的位置记；`tests/LineRules.test.ts` 查位置仍指着原来那句）。

**固定日的天气写死**已解决（CHANGELOG 2026-10-08 续八）：按作者的决定，像 Day 22 一样在 `FORCED_WEATHER` 写定——Day 21、28、29、30 霜冻，Day 27 晴。Day 28、29 是为 Day 30 早晨"这几天每天都有霜"补的，作者没点名，可以撤。

## 5. 远期想法

作者 2026-11-16 提的，都还没有定，也没有排期。每一条写三样：是什么，现在有什么可以接，动手之前要先定什么。建议的顺序是 5.1 → 5.2 与 5.3 → 5.4；5.5、5.6 与它们无关，随时可以单做。

### 5.1 把条件文本搬进 JSON

- **是什么**：给文字变体一套小的条件写法（旗标、信任档、天气、日期、时段），和文字写在一起。这样加一句“世界记得你做过什么”的回应只改内容文件，不碰代码。作者举过的例子：头一场雨马厩的桶漏了，花木材修；下一场雨桶不在了；再往后一起干活时，格雷格已经把工具摆好。
- **现在的样子**：文字在 JSON，“什么时候用哪一段”在代码。18 个事件、83 段变体，由 `EventSystem.ts` 里约二十个手写的 `processXxx` 函数挑。项目里已经有三种互不相干的小条件写法：见闻的解锁（`CodexCondition`：认识、信任、旗标、任一）、闲笔的出现条件（`config.ts` 的 `LineRule`，按句子在池里的位置记）、事件变体的天气与时段（`variantRules`）。选项写旗标本来就在 JSON（`effects.flags`），所以统一之后整条回应链都是数据。
- **顺带的好处**：差异提示可以直接接上，槽位是这句话，键是命中的那个条件。
- **代价**：审查工具（`npm run audit`）、剧情文本稿的导出导入、文本工作台和测试都要认识新写法；挑段落的同时还改数值的那些函数留在代码里。
- **时机**：作为 5.2 的第一步，不提前做。

### 5.2 后日谈

- **是什么**：角色在故事之后的生活。
- **可以接的**：结局尾声里路德维希已经按结局写了不同的三天（GDD_NEXT 10.3、10.4）；见闻跨季保留；“没有走到的地方”已经在结局之后占了一行，证明结局下面放得住安静的东西。
- **我的建议**：每个人一组带条件的段落（信任档、旗标、哪个结局），用 5.1 的写法；只给这一季真正认识了的人，和行囊“只画已经有的”一个道理；读过的可以进见闻，成为跨季的一层。
- **要先定**：放在哪（结局正文之后、回望、见闻）；写哪些人；4A、4B 是否各写。文字由作者写。

### 5.3 真相结局的奖励

- **是什么**：只有真相结局才有霍特曼的后日谈，所以给这个结局一样别处没有的东西，比如他的视角：烧掉的东西，八个十月的笔迹。
- **可以接的**：文书已经可以点开读全文（`DocumentSystem`、`DocumentReader`，古语与通用语对照的那种排法也在）；见闻和结局收藏跨季保留。
- **要先定**：形式（一份文书，还是几页笔迹的图）；放在哪。行囊只管这一季，结局之后不再翻，所以要长期留着就放进标题页的“回望”（现在是见闻、结局两页，可以加第三页）；4A 与 4B 给的是否相同。
- 奖励是让玩家多知道一点，不做成成就或分数。工程量小，主要是作者的写作量。

### 5.4 冬季或第二任期（DLC）

- **是什么**：秋收之后再过一季，探索枫径庄园附近的其他地方：河谷城、林地、其他庄园、地方神殿，乃至其他公国。
- **现在的样子**：引擎把“一季”写死了：30 天（`TOTAL_DAYS`）、一张按日期排的固定事件表、按日的天气和三幕的起止，`createInitialState(seed)` 也没有“带过来的状态”这个入口。
- **要做的**：把一季变成可以换的数据包（日历长度、事件表、天气、地点）；从秋季结局带过去的状态（资源、关系、旗标、哪个结局）；存档版本要升；庄园外的地点和行程（GDD_NEXT 3.4 已有行程时长）。5.1 做了之后，带过去的旗标可以直接驱动文字。
- **不受影响的**：已读记录、见闻、结局收藏本来就不属于哪一季。
- 最大的一项，放在最后。

- **要先定**：放在哪几处（开场、换幕、结局）；什么形式（静帧淡入、几格手绘、文字排版的动画）；多长。
- **做的时候要守的**：能用空格跳过，按住不会连跳（键盘的规则已经有）；系统设了“减少动态效果”的人看到的是静帧；单文件构建会把图内联，注意体积。

### 5.6 音乐：维瓦尔第的变体

- **是什么**：作者手里有一段维瓦尔第曲子的变体版本，想在某个场景播放。
- **现在的规则**（GDD_NEXT 13.2a）：赛季里不放音乐，音乐只在标题页和结局之后（`SOUND_LIST.md` 另列了第 30 天夜晚）。`mus_title`、`mus_end` 两个位置已经接好，只是没有文件：把文件按这个名字放进 `src/assets/audio/` 就会响，不用写代码。
- **两条路**：一是放在已有的位置（标题页或结局），规则不动。二是放进赛季里的某一场，这要么由作者改“局内不放音乐”这条，要么让它是那一场里真的有人在演奏的音乐（磨岭的晚宴、猎季的营火），那样它仍然是写实的声音；这条路要加一个 cue 和它响起的时刻。
- **我的联想，不是作者说的**：如果是《四季》里的“秋”，第三乐章写的是狩猎，和第 18 到 21 天的猎季对得上。
- **要先定**：是哪一首、放在哪。**动手之前要有**这个版本的来源与许可：曲子本身早已是公有的，改编和录音各有各的权利，要能写进 `SOUND_CREDITS.md`，才能进公开的仓库和 itch。另外看时长和体积（单文件构建会内联）。
